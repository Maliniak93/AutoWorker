# App skeleton, health page and ADR-002

Issue #4 · Kind: New · Tier: 2 · Branch: `feat/tech-stack-app-skeleton`

## Goal

A Fastify + TypeScript server with a React + Vite health page and a JSON health endpoint runs from `npm start` in WSL2/Linux, is covered by Vitest tests (including a node-pty smoke test), is checked by Code `format`/`build`/`test` steps in `node scripts/verify.mjs`, and ADR-002 records the stack.

## Why

Part 1 of the tech-stack epic (roadmap step 1). Today there is no `src/`, no `package.json`, and `verify.steps` holds only `scripts-test` (`docs/plan/architecture.md` → Current vs target), so no Code change can be built or verified.

## Design decisions

- Stack, terminal path, state storage, Docker login and platforms: see the epic's Design decisions; this part writes them down as **ADR-002 ✅**, with three short sections: the decision, the alternatives rejected (Python/FastAPI: two toolchains; C#/ASP.NET Core: no maintained Linux PTY library; Express/Hono; htmx), and the feasibility result (the smoke-test output from AC-9/AC-10 on the build machine, and how Claude Code logs in inside Docker via `CLAUDE_CODE_OAUTH_TOKEN`).
- Server TypeScript runs through Node's native type stripping: `tsconfig.json` sets `noEmit`, `allowImportingTsExtensions`, `erasableSyntaxOnly`, `verbatimModuleSyntax`; relative imports use the `.ts` extension. No `tsx`/`ts-node`.
- The client builds to `dist/client`; the server serves it with `@fastify/static` and falls back to `index.html` for unknown non-`/api` GET routes (SPA). `npm start` therefore always builds first (`prestart`).
- `buildApp({ probe })` takes the tool prober as a dependency so tests can fake a missing tool; `main.ts` passes the real one. Tests drive the server through `app.inject()`, not a real socket, except the busy-port test.
- Health payload: `{ status: "ok", version, tools: { claude, git, gh } }`, each tool `{ status: "ok" | "missing", version?: string }`, `gh` also `loggedIn: boolean`. `version` comes from `package.json`. A tool is probed with `<tool> --version` (5 s timeout, all in parallel); `gh` login with `gh auth status` exit code. A probe never throws: any spawn error or timeout is `missing`.
- `loadConfig(env)`: `HOST` default `127.0.0.1`, `PORT` default `4280`; an invalid `PORT` (not an integer 1–65535) throws with a message naming `PORT`.
- Busy port: `main.ts` catches `EADDRINUSE`, prints one line `Port <n> is already in use — set PORT in .env to use another one.` and exits with code 1. No port auto-picking.
- `.env.example` lists `HOST`, `PORT`, `AUTOWORKER_DATA_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `GH_TOKEN`, each commented; a missing `.env` is fine (`--env-file-if-exists`).
- The test-writer runs first on a repo with no `package.json`: it may create `package.json`, `tsconfig.json` and `vite.config.ts` with the test tooling (Vitest, jsdom, Testing Library) it needs to run red; the implementer owns them afterwards.
- `node-pty` needs `build-essential` + `python3` in WSL; build this part in WSL2 (not native Windows), where `verify.mjs` must also run.
- No hard rule changes in this part; ADR-002 is the ADR that part 3's application rules in `CLAUDE.md` rest on.

## Acceptance criteria

- [ ] **AC-1** Given the app is built with all tools present, when `GET /api/health` is called, then it answers 200 with `status: "ok"`, the `package.json` version and `claude`, `git`, `gh` each `status: "ok"`. — proof: `tests/server/health.test.ts` › `GET /api/health returns 200 with version and ok tools`
- [ ] **AC-2** Given the prober reports `gh` missing, when `GET /api/health` is called, then it still answers 200 and `tools.gh` is `{ status: "missing", loggedIn: false }`. — proof: `tests/server/health.test.ts` › `a missing tool is reported as missing without failing the endpoint`
- [ ] **AC-3** Given `gh` is present but `gh auth status` fails, when `GET /api/health` is called, then `tools.gh.loggedIn` is `false` and `tools.gh.status` is `ok`. — proof: `tests/server/health.test.ts` › `gh logged out is reported as loggedIn false`
- [ ] **AC-4** Given a command name that does not exist on PATH, when `probeTool` runs, then it resolves to `{ status: "missing" }` without throwing; given `node`, it resolves to `ok` with a version. — proof: `tests/server/tools.test.ts` › `probeTool reports missing for an unknown command` and `probeTool reports ok with a version for node`
- [ ] **AC-5** Given no `HOST`/`PORT`, when `loadConfig` runs, then it returns `127.0.0.1` and `4280`; given `PORT=4290` it returns 4290; given `PORT=abc` it throws naming `PORT`. — proof: `tests/server/config.test.ts` › `loadConfig defaults`, `loadConfig reads PORT`, `loadConfig rejects an invalid PORT`
- [ ] **AC-6** Given another server already listens on the chosen port, when the app starts, then the process exits with code 1 and prints one line naming the port and `PORT`. — proof: `tests/server/main.test.ts` › `a busy port exits with code 1 and a PORT hint`
- [ ] **AC-7** Given a built client, when `GET /` is requested, then it answers 200 HTML that loads the SPA; `GET /settings` (an unknown client route) also returns that `index.html`, while `GET /api/unknown` returns 404. — proof: `tests/server/static.test.ts` › `serves the SPA and falls back for client routes only`
- [ ] **AC-8** Given `/api/health` returns version `0.1.0` with `gh` missing, when `App` renders, then it shows "AutoWorker", `0.1.0`, `claude` and `git` as ok and `gh` as missing. — proof: `tests/client/App.test.tsx` › `shows the version and each tool status`
- [ ] **AC-9** Given `node-pty` is installed, when the smoke test spawns `node --version` in a PTY, then the output matches `v<major>.` and the exit code is 0. — proof: `tests/pty.test.ts` › `node-pty runs node --version`
- [ ] **AC-10** Given `claude` is on PATH, when the smoke test spawns `claude --version` in a PTY, then it exits 0 with a version line (the test is skipped only when `claude` is not on PATH, and says so). — proof: `tests/pty.test.ts` › `node-pty runs claude --version`
- [ ] **AC-11** Given a change under `src/`, when `node scripts/verify.mjs` runs, then the `format`, `build` and `test` steps run (and `--quick` runs `format` and `build`); a failing Vitest test makes it exit non-zero. — proof: `node scripts/verify.mjs --all` green, and `node scripts/areas.mjs of package.json tsconfig.json vite.config.ts .env.example` prints `Code` for each
- [ ] **AC-12** Given the repo after this part, when `docs/plan/decisions.md` is read, then it has `## ADR-002 ✅` naming the stack, the rejected alternatives, the feasibility result and the Docker login via `CLAUDE_CODE_OAUTH_TOKEN`; `docs/plan/architecture.md` has no "not designed yet" text. — proof: `grep -n "## ADR-002" docs/plan/decisions.md` and `grep -c "not designed yet" docs/plan/architecture.md` → 0

## Manual test

**Preparation**

1. In WSL2: `sudo apt install -y build-essential python3`, Node ≥ 22.18, `git`, `gh` (logged in) and `claude` on PATH.
2. Clone the repo to `~/code/AutoWorker` (WSL filesystem), `git switch master && git pull`, `npm ci`; no `.env` file.

**Steps**

1. `node scripts/verify.mjs --all` → `scripts-test`, `format`, `build`, `test` all green.
2. `npm start` → log shows the server listening on `http://127.0.0.1:4280`.
3. Open `http://localhost:4280` (from Windows too) → page titled "AutoWorker" with version `0.1.0`.
4. Same page → `claude`, `git`, `gh` ok and `gh` logged in.
5. `curl -s http://localhost:4280/api/health` → JSON with `status: "ok"`, `version: "0.1.0"`, three tools.
6. Open `http://localhost:4280/anything` → the same page (SPA fallback); `curl -si http://localhost:4280/api/nope` → 404.
7. Start a second `npm start` in another shell → it exits with code 1 and one line saying port 4280 is in use and to set `PORT`.
8. Stop the app, `gh auth logout`, `npm start`, reload → `gh` ok but not logged in; log back in with `gh auth login`.
9. `PORT=4290 npm start` → page on `http://localhost:4290`.
10. Break the version in `src/server/health.ts`, `node scripts/verify.mjs` → `test` step red; revert → green.

## Verification

`npm ci` in WSL2, then `node scripts/verify.mjs --all` (runs every proof test through the `test` step plus format and build); `npx vitest run tests/pty.test.ts` shows whether AC-10 ran or was skipped; the two `grep` commands for AC-12.
